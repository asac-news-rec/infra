# ADR-003: 로깅 서버는 이벤트를 메모리에 모았다가 JSONL.gz로 GCS에 직접 저장한다

## 상태
Accepted (방향: 멘토 권고, 2026-11-03) / 세부 항목은 Proposed (세호 님과 조율 필요)

## 컨텍스트
현재 설계(세호 님 명세와 로컬 코드)는 받은 이벤트를 SQLite에 먼저 저장하고 응답한 뒤, 파일로 내보낸다. 로깅 서버는 Cloud Run에 배포하는데 Cloud Run은 디스크가 유지되지 않는다. 멘토는 DB에 직접 쓰면 서버가 터질 수 있다고 했다.

## 결정
로깅 서버는 이벤트를 **메모리에 모았다가** 일정 건수(예: 100건) 또는 일정 시간(예: 몇 초)마다 **JSONL로 압축(gz)해 GCS에 직접 저장**한다. 폴더는 5분 파티션(`date=/hour=/minute=` 아래 `served/`, `actions/`)이고 `_SUCCESS`는 만들지 않는다.

## 근거
- DB 쓰기 병목과 Cloud Run의 디스크 비유지 문제를 함께 피한다.
- 이후 단계(Airflow 센서, BigQuery 적재)가 파일 기반이라 구조가 단순하다.

## 결과 (조율이 필요한 세부)
- 응답 `accepted`의 의미: "메모리에 받았다"인가 "GCS에 저장했다"인가.
- 서버가 꺼질 때 메모리에 있던 기록이 유실될 수 있다. 허용 범위와 저장 주기를 정해야 한다.
- 인스턴스가 여러 개 떠도 파일 이름이 겹치지 않게 인스턴스 ID를 넣는다.
- 같은 `event_id` 중복 제거는 정제 단계에서 한다.
- 로깅 서버 서비스 계정에 버킷 쓰기 권한이 필요하다(Terraform).
- 세호 님이 코드(저장 계층, 테스트, `/ready` 등)를 바꿔야 한다.

## 대안
- SQLite 유지: Cloud Run에서는 맞지 않는다. GKE와 영구 디스크를 쓰면 가능하지만 멘토 지시와 다르다.
- Pub/Sub → GCS: 확장 후보(10/31에 확장 자리만 그리기로 함).
- Cloud SQL에 직접 쓰기: 멘토가 부하 위험을 지적했다.
