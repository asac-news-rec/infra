# ADR-003: 로깅 서버의 이벤트 저장 방식 (검토 중)

> 파일 이름은 11/3 멘토 권고안 기준입니다. 결정이 나면 이름과 상태를 갱신합니다.

## 상태
Proposed (2026-11-06). 11/3 멘토 권고(메모리에 모았다가 GCS에 저장)는 방향 제안이었고, 11/5 멘토링에서 멘토가 "정답은 정해 주지 않는다. 팀이 장단점을 표로 비교해 결론을 통보하라"고 했다. 결정되면 `Accepted`로 바꾸고 이 문서를 갱신한다.

## 컨텍스트
- 현재 로컬 초안(세호 님 명세와 코드)은 받은 이벤트를 SQLite에 먼저 저장하고 응답한 뒤 파일로 내보낸다. 클라우드의 로깅 서버(Cloud Run)는 아직 만들지 않았고, 11/5 회의에서 세호 님이 "로그 서버는 없다"고 확인했다.
- Cloud Run은 로컬 디스크가 유지되지 않고, 종료 신호를 받은 뒤 약 10초 안에 정리해야 한다. 기본 설정에서는 응답 뒤 백그라운드 작업이 멈출 수 있어 "CPU 항상 할당" 설정이 필요하다 **[확인 필요]**.
- 세호 님(11/5): 메모리에만 두면 서버가 꺼질 때 유실 위험이 있어 Pub/Sub가 필요하다는 의견.
- **근거 문서 확인 중**: 리뷰에서 "로깅 서버 README의 Pub/Sub 발행·응답 계약"이 언급되었으나 조직의 5개 저장소에서 해당 README를 찾지 못했다. SQLite 초안과 Pub/Sub 약속 중 어느 쪽이 최신인지는 세호 님께 확인 중이며, 확인되면 문서 위치를 여기에 적는다 **[확인 필요]**.
- 멘토(11/5): SQLite도 가능(쿠버네티스에서 디스크를 붙이는 방법), 아웃박스 패턴도 있다. Pub/Sub는 다시 처리할 때 중복이 생기고 받는 쪽 손실도 고민해야 한다.

## 결정
아직 정하지 않았다. 후보 세 가지를 아래 기준으로 비교해 팀이 정한다.

| 후보 | 장점 | 단점 |
|---|---|---|
| ① SQLite에 먼저 저장 | 구현 쉬움, 받자마자 디스크에 저장 | Cloud Run의 디스크는 임시라 인스턴스가 사라지면 같이 사라짐. 쿠버네티스 디스크 마운트나 DB 사용이 필요 |
| ② 메모리에 모았다가 GCS에 저장(11/3 권고) | 가장 단순, 파일이 바로 Airflow 입력 | 종료 때 메모리 유실. 종료 신호 처리와 CPU 항상 할당 필요 |
| ③ Pub/Sub를 거쳐 GCS에 저장 | 받은 즉시 보관되어 유실 위험이 가장 작음. Cloud Storage 구독으로 코드 없이 파일 저장 가능 | 부품 증가(토픽, 구독, 권한), 중복 가능(이벤트 ID로 제거), 파일 형식·압축 제약 **[확인 필요]** |

**비교 기준**: ① 유실을 얼마나 허용하나(서버가 꺼질 때 최근 몇 분) ② 구현·운영 난이도 ③ 비용.

## 근거
- 모든 기술에는 트레이드오프가 있어 정답은 없고, 기준에 맞춰 근거를 남긴다(멘토 11/5).
- 이후 단계(Airflow 센서, BigQuery 적재)가 파일 기반이므로 어느 후보든 최종 저장물은 GCS 파일이다.

## 결과 (결정 뒤 인프라 영향)
- ②를 고르면: 로깅 서버(Cloud Run)에 종료 신호 처리와 "CPU 항상 할당" 설정이 필요하다.
- ③을 고르면: Pub/Sub 토픽과 구독, 로깅 서버 서비스 계정의 발행 권한, 구독의 버킷 쓰기 권한을 Terraform으로 준비한다.
- 어느 쪽이든 응답 `accepted`의 의미("받았다"인가 "저장했다"인가)와 파일 이름 규칙(덮어쓰기 불가 문제 포함)을 정해야 한다.
- 세호 님이 코드(저장 계층, 테스트, `/ready` 등)를 바꿔야 한다.

## 대안
- Cloud SQL에 직접 쓰기: 멘토가 부하 위험을 지적했다.
- 아웃박스 패턴: 멘토가 예로 든 방법으로, DB를 우체통처럼 쓰는 방식이다. 후보에 추가할지 팀이 판단한다.
