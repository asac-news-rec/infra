# 아키텍처 개요

> Last Updated: 2026-11-03

프로젝트의 전체 그림과 설계 결정을 담은 문서입니다. 파일별 책임은
`agent-project-reference.md`를 참고합니다. 상태 표기(**[현재]** / **[계획]** /
**[미정]**)는 `CLAUDE.md`를 따릅니다.

> 이 그림은 멘토링(10/28, 10/31)과 팀 회의 내용을 바탕으로 한 **설계안**입니다.
> 구현된 것이 아니며, 팀 확정 전 항목이 있습니다. 가장 상세한 설계는
> `blueprint` 저장소를 참고합니다.

## 시스템 맥락

ASAC 파이널 프로젝트(뉴스 추천 시스템)의 목표는 "뉴스 앱을 만들고, 사용자가
누른 기록(로그)을 모아, 그 기록으로 클릭 확률을 예측하는 모델을 학습시켜, 다음
방문 때 그 순서로 보여주는 한 바퀴를 끝까지 돌리는 것"입니다. 이 저장소는 그
워크로드가 실행될 기반(로컬 개발 환경, 클라우드 인프라)을 제공합니다.

## 데이터 흐름

```
프론트 ──피드 요청──▶ 뉴스 백엔드 ──후보 기사──▶ 추론 서버 ──피처 조회──▶ Valkey
  │                      │   ▲                      ▲
  │                      │   └──── 점수 응답 ────────┘   (추론 서버는 기동 시
  │                      │                              MLflow에서 모델을 받음)
  │                      └─ 반환 기록(served) ──┐
  └─ 행동 이벤트(exposure, article_open 등) ────┴▶ 로깅 서버 ──▶ GCS (5분 파티션)
                                                                 │
                                          Airflow (매시간, 센서로 폴더 감지)
                                                                 ▼
                                      BigQuery(정제·집계·피처) ──▶ 모델 학습 ──▶ MLflow + GCS
                                                      └─────▶ Valkey (최신 피처 갱신)
```

| 단계 | 하는 일 | 상태 |
|---|---|---|
| 수집 | 프론트가 보낸 행동 JSON과 백엔드가 만든 반환 기록을 로깅 서버가 GCS에 파일로 저장 | [계획] |
| 파티션 | 이벤트 시각 기준 5분 단위 폴더에 저장. 완료 표식 파일(`_SUCCESS`)은 쓰지 않음 | 멘토 방침 |
| 가공 | Airflow가 매시간(예: 10:10~15분) 돌며, 센서가 앞 시간대 폴더를 확인한 뒤 BigQuery로 정제 | [계획] |
| 피처 | 같은 계산 결과를 BigQuery(학습용, 시점별 이력)와 Valkey(서비스용, 최신값) 두 곳에 씀 | [계획] |
| 학습 | BigQuery 데이터로 모델 학습, 결과를 MLflow에 버전으로 등록하고 파일은 GCS에 저장 | [계획] |
| 서빙 | 추론 서버가 기동할 때 MLflow의 Production 모델을 받아 메모리에 올리고 점수 계산 | [계획] |

## 환경 구성

```
[로컬] 팀원 PC ── Docker Compose (compose/)
        ├── Postgres ── 뉴스 DB / Airflow 기록 / MLflow 기록
        ├── Airflow ── 배치 실행
        ├── Valkey ── 온라인 피처 저장
        ├── MLflow ── 모델 기록
        ├── 가짜 GCS (fake-gcs-server) ── 클라우드 계정 없이 센서·파일 적재 시험
        └── backend / frontend / logging / inference ── 자리만 (각 담당이 이미지 연결)

[클라우드] GCP (계정 발급 후, 프로젝트 1개) ── Terraform + Helm으로 코드화
        ├── GKE ── Airflow, 추론 서버, MLflow (직접 설치)
        ├── Cloud Run ── 프론트, 백엔드 (외부에 노출되는 서버)
        ├── Cloud SQL (PostgreSQL) ── 뉴스 DB
        ├── GCS ── 원본 로그, 모델 파일, 기사 이미지
        └── BigQuery ── 정제·집계·피처 테이블
```

## 주요 설계 결정

### 로컬 우선: compose가 dev 환경 역할
- 클라우드 환경을 둘로 나누면 비용이 두 배가 되므로, 클라우드 프로젝트는 1개로
  두고 개발 환경은 로컬 compose가 맡습니다.
- 클라우드 전용으로 확인할 것(IAM, GKE 배포, 실제 GCS·BigQuery 적재, 네트워크)은
  계정 발급 후 연결합니다.

### 계정 교체 대비: Terraform으로 재생성
- 클라우드 계정은 약 6주 뒤 교체될 수 있습니다. 계정마다 달라지는 값(project id,
  버킷 이름)은 변수로 받고, 새 계정에서 같은 코드를 적용하면 환경이 복원되게
  합니다.

### 원본은 먼저 쌓고, 가공은 나중에
- 이벤트는 가공하지 않은 원본 그대로 GCS에 시간 폴더별로 쌓고, 정제는 Airflow
  배치가 다음 단계로 합니다. 수집 서버는 이벤트의 의미를 해석하지 않습니다.

### 피처는 두 벌: 학습용과 서비스용
- 학습용은 시점별로 덮어쓰지 않고 이력을 남겨, 학습 때 "사건 직전 시점"의 값만
  붙입니다(정답이 입력에 새는 것을 방지).
- 서비스용은 요청 순간에 빠르게 꺼내 쓰도록 최신값을 Valkey에 둡니다.

### 시크릿: 코드와 분리
- 로컬은 `.env`(커밋 금지)와 `.env.example`(이름 목록만 공유), 클라우드는
  Secret Manager를 사용할 계획입니다. 값은 output·로그·채팅에 노출하지 않습니다.

### 비용: 쓰지 않을 때 줄이기
- 예산이 정해져 있으므로 켜 두는 동안 과금되는 리소스(GKE 노드 등)는 쓰지 않을
  때 줄이거나 지웁니다. Terraform으로 다시 만들 수 있게 해 둡니다.

## 현재와 계획

| 항목 | 현재 | 계획 |
|---|---|---|
| 에이전트 하네스·협업 규칙 | 이식 완료 (이 문서들) | 팀 상황에 맞게 갱신 |
| 로컬 개발 환경 | 없음 | `compose/` (11/5 공유 목표) |
| 클라우드 | 계정 미발급 | 계정 발급 후 Terraform·Helm |
| CI | 브랜치 이름 검사, Claude 리뷰(secret 등록 전) | 필요에 따라 검증 workflow 추가 |
| 배포 | 없음 | 클라우드 구성 후 검토 |

## 미정

- 계정 발급 시점, 예산 단위(두 달 $1000의 기준)
- 로깅 서버 실행 위치(Cloud Run / GKE)와 백엔드와의 분리 여부
- Valkey 매니지드/직접 설치, GKE 운영 모드와 노드 수
- 추론 서버 담당자
- GCS 폴더 이름 규칙, 이벤트 필드 이름(`user_id` / `reader_id` 등)

## 변경 영향 체크리스트

아키텍처에 영향을 주는 변경 시 확인합니다:

- [ ] 데이터 흐름(수집→저장→가공→학습→서빙)의 연결이 바뀌는가
- [ ] 다른 팀원의 저장소(`backend`, `frontend`, `data-ml-pipeline`)의 설정이나 접속 방식에 영향이 있는가
- [ ] 로컬(compose)과 클라우드 양쪽에서 같게 동작하는가
- [ ] 비용과 계정 교체(재생성 가능성)에 영향이 있는가
- [ ] 이 문서와 `agent-project-reference.md`의 갱신이 필요한가
